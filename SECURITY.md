# Security

[PRODUCT](PRODUCT.md), [PHASE_0 §10](PHASE_0.md#10-security--privacy-model) define approved policies; this file separates present Foundation controls from future controls.

## Implemented Foundation controls

Strict TypeScript; server-only DB/env/logger/auth factory/services; lazy env validation without value echo; explicit error DTO with static messages, no SQL/stack/cause. Logger drops arbitrary runtime keys and accepts opaque IDs/static action names only. Secrets remain ignored `.env*` (exception `.env.example`), never NEXT_PUBLIC DB/auth/provider secrets. CI has read-only repository permission, no deployment and no production credentials. Browser receives auth forms and safe account DTOs, never the DB client or secret configuration. Basic nosniff/frame/referrer headers, no wildcard CORS. Generated client/build/cache ignored. No real secret generated by setup.

## Phase 2 controls

Better Auth 1.7.7 manages password hashing, verification/reset expiry and session lifecycle. Passwords are 12–128 characters for signup/reset; verified email is required before credential sign-in; signup does not create a session or grant roles. Session cookies are HttpOnly, SameSite=Lax and Secure in production, with seven-day expiry/daily refresh. Cookie cache is off; protected requests validate sessions and read current identity/roles/status from PostgreSQL. No localStorage auth, process-memory session persistence or cookie-presence authorization. Password reset revokes other sessions. Real PostgreSQL tests verified expired/reused reset rejection, consumed hashed reset identifiers, logout invalidation, fixation resistance, cross-instance sessions/rate limits, roles/status guards and non-enumerating unknown-account reset. Verification email uses Better Auth's signed expiring token rather than a database verification row; reset tokens use expiring/consumed Verification rows.

Strict signup input rejects role/roles/status/emailVerified/extra fields; status is also Better Auth input:false and returned:false. Normal-role action accepts only WORKER/EMPLOYER and server-derived userId. Compound PK plus lock/upsert prevents duplicate roles; account status is re-read under that lock. Suspended authentication can read the account, but new activity/role activation requires ACTIVE; ADMIN cannot bypass it. BANNED denies the same scoped action while full ban/active-obligation semantics remain D5. No premature Engagement policy exists.

Public POST auth and role routes require exact configured Origin and reject cross-site Fetch Metadata. Missing/null origins fail closed. JSON-only 16 KiB bounded inputs and endpoint allowlists reduce exposed surface. Better Auth's CSRF/origin/redirect checks remain enabled; no wildcard CORS. UI redirect/disabled controls are not security. Internal auth API calls bypass Better Auth HTTP rate limiting, so public auth flows go through its handler; rateLimit.storage=database is explicitly enabled with endpoint limits. Confirm trusted proxy/IP forwarding for the managed host before public release; with no trusted IP, Better Auth uses a shared per-path bucket rather than claiming per-client isolation. No Redis is needed for this foundation.

Auth URLs are fixed local paths; arbitrary redirect/callback input is rejected. Mail URLs carry token fragments, never query tokens in public page access logs; the client clears fragments from history and submits POST. Public GET verification is denied; the library's GET verification handler is used only internally after the POST origin check. No raw Better Auth mutation payloads/session tokens/errors are returned. Auth library logging is disabled; Next after retains email delivery work and only logs a fixed failure event. No fire-and-forget task depending on the operator PC. Production platform/proxy request-body logging must also stay disabled. Auth-token pages use no-referrer/no-store and no analytics.

Resend is a replaceable email adapter with server env credentials; missing provider config returns a safe service error before signup/reset request proceeds. Background delivery errors do not expose addresses/provider bodies/tokens. Local manual testing may use a configured sender and operator-controlled recipient; tests use only their fake adapter. No debug token endpoint, inbox file or log-token bypass exists. Build/public pages do not require configured providers.

The HTTP test's scripts/auth-test-mail.mjs preload is never imported by application code. It requires explicit disposable/development test flags and a loopback-only inbox; it intercepts Resend transport only inside the child test process. Tokens remain in test memory while actual Next routes, Better Auth and PostgreSQL execute unchanged. Runtime has no new test email provider or localhost fallback. CI uses a fresh PostgreSQL service and disposable credentials, with no real mail/provider/production secrets. Tests do not weaken rate limits: unique test client networks prevent repeat-run interference, and a separate auth instance must still receive HTTP 429 from the persisted counter. Test server and owned records are cleaned up afterward.

### Trusted ADMIN provisioning (operational only)

No public/admin-registration API or Better Auth admin plugin is installed. A trusted operator with direct, least-privileged DB access must first create/verify the intended identity through normal auth, review the exact user ID and operational change ticket, then use a transaction locking User. Recheck ACTIVE and emailVerified, insert UserRole(ADMIN) with grantedBy set to the reviewed operator/change reference, and retain the approval in the operator's audit system. Use bound parameters, idempotent grant and independent review; do not grant by browser-supplied role or unverified email alone. Revocation deletes that role through an equally reviewed operational action; current-role queries take effect on the next request. This is a documented provisioning procedure, not a new moderation/audit dashboard or a claim that future immutable business audit has been built.

The logger's allowlist does not make user text safe: never put email/password/message into requestId/action/resourceId. Future request context must generate correlation IDs server-side. Error mapper caller supplies generated safe requestId, not untrusted input. Zod callers must whitelist inputs and map safe field errors rather than serializing issues.

## Phase 3 controls and review

Profile/company services are server-only. Every call rereads current User roles/status; writes lock User before any Company lock and recheck current membership under that Company lock. Revocation uses the same Company lock. Other-profile mutation returns safe 404; missing membership returns safe 404; insufficient current role returns safe 403. A creator who leaves has no management/retry authority. ADMIN is not a discovery/company bypass. SUSPENDED/BANNED deny new marketplace activity; own reads and privacy opt-out remain allowed.

No public Worker directory exists. Discovery requires a real session + ACTIVE EMPLOYER + EmployerProfile; targets are opted-in ACTIVE WORKERs. Discovery DTO fields are profile ID, identity display name, headline, coarse city, work preferences/modes, skill name/level and a supplied/not-specified availability indicator. It omits identity userId, email/phone, bio, exact schedule/timezone, status/moderation, auth/session and verification data. Self DTOs are owner-scoped. OWNER member roster has only opaque memberId needed for removal, displayName and role; MANAGER cannot read that roster. There is no public Company endpoint in this phase, only safe current-membership views.

Strict Zod schemas reject mass assignment of identity, role, ownership, verification, discoverability-on-profile-save and completeness. UUID resource IDs/opaque bounded membership IDs, safe HTTP(S)-only website strings (no URL credentials), 16 KiB JSON limits, exact-origin mutation guards and method/path/query allowlists apply. Websites are stored text, never fetched server-side. Unknown/duplicate query keys and oversized page/cursor inputs fail safely. Public errors contain static categories/messages only, not raw validation issues, SQL or payloads. No profile input is logged.

New Worker profiles default discovery off; explicit toggle is separate from saving. Incomplete drafts may opt in: completeness is informational and no apply action exists. Users control their own headline/name text, so these coarse fields are not an automatic PII-redaction system. City rejects digits and UI requests only province/city, not a home address. Private pages/APIs use no-store; profile/company pages use no-referrer. No cache of discovery or membership entitlement is introduced.

Company slug is server-derived with a random suffix/unique index and bounded whole-transaction retry. Creator/key replay checks current membership and current company contents under lock. Company/initial OWNER are atomic, duplicate memberships are DB-rejected, at-most-one OWNER has a partial unique index and public OWNER removal is rejected. No member-add, invitation, transfer, grant, verification or legal-document endpoint exists. Trusted SQL writers still require review and this lock/invariant protocol; DB administrator privileges are not constrained by application policies.

Actual PostgreSQL tests verify concurrent duplicate creation, database constraints, current roles, cross-profile/company denial, opt-in/withdrawal, DTO projection/pagination, final OWNER protection, in-flight Company-lock revocation and User-lock suspension, and creator departure. Real Next HTTP tests verify sessions, roles, safe statuses, Origin, profiles, discovery, company/member allowlists and suspended privacy opt-out while retaining all Phase 2 auth regression. No production preloader, secret, document or runtime local persistence was added. Abuse thresholds/CSP/cloud TLS/proxy and public release hardening remain their approved later phases; this report does not claim a production penetration test.

## Phase 4 controls

Job services re-read current identity/status/EMPLOYER/EmployerProfile and current ownership on every request. Mutations lock User → Company or personal EmployerProfile → Job; membership revocation uses that same Company lock. Job version rejects stale requests. Personal ownership derives from EmployerProfile; company authorization derives exclusively from current OWNER/MANAGER membership, never creator or an owner flag. ADMIN alone has no bypass. Unverified ACTIVE employers may prepare drafts; publishing/resuming and editing active terms require fresh verified email. SUSPENDED/BANNED deny new recruiting activity; authorized pause/close/cancel remain permitted, with all other ownership/role/state checks intact. Full ban and active hiring obligation semantics remain D5/Phase 5.

Only explicit lifecycle actions are exposed; status/provenance/owner/version mass assignment is rejected. Company may be chosen on creation only with current membership; no ownership-move endpoint exists. Close/cancel are distinct terminal actions, completion is inaccessible, duplication creates fresh DRAFT terms/provenance/timestamps. Actor-bound retry keys recheck ownership and terms and cannot turn the source into its own duplicate. Publication counts PUBLISHED+PAUSED inside the owner transaction, separately three per profile/company. No browser quota or process-memory locks authorize transitions.

Public queries allow only PUBLISHED ads and explicit DTO fields. No identity owner IDs, private contacts, raw account status, membership or moderation metadata is returned. Unknown/duplicate query keys, malformed cursor, protected fields, invalid money/date/schedule/headcount/skills and stale versions produce safe errors. JSON remains bounded at 16 KiB and mutations exact-origin. Authenticated management uses separate endpoints and no-store; public reads are also no-store to reflect lifecycle changes. Employer text is escaped but may contain voluntary contact text; the coarse schema is not a PII detector. No exact address/GPS field exists. Automatic owner-status hiding and abuse thresholds remain deferred moderation/release work, not implemented silently.

Pure tests plus dedicated actual PostgreSQL jobs and extended Next HTTP tests cover state/term projection, quota races, DB constraints, IDOR, current membership/role/status, creator departure, draft visibility, verified email and restrictive suspension actions. The HTTP preload still intercepts only test email. No business audit subsystem, hiring tables, uploads, deployment or production filesystem persistence is introduced. See PHASE_4 for verified outcomes rather than treating authored tests as evidence.

## Phase 5 hiring protections

Every Application/Offer/Engagement operation resolves relational ownership from the database after a real session check. Worker identities come from the session's current WorkerProfile; Company authorization/self-application uses current OWNER/MANAGER membership. UUIDs, creator provenance, browser role/status and request ownership fields grant no authority. Employer applicant lists require an owned Job and are bounded (12 default/30 max); Worker lists are self-only. Public Job APIs never include applicants or raw snapshots. Offer history is separately bounded.

Canonical locks extend Phase 4: actor User→Company/personal EmployerProfile→Job→Application→Offer→Engagement. Membership revocation uses the same Company row; role/status/profile writes use User. Atomic acceptance and every Engagement capacity change serialize under Job. Lifetime application uniqueness, one pending Offer, revision/retry uniqueness, one Engagement per Application/Offer and composite consistency FKs are PostgreSQL enforced. Offer terms/identity/time and accepted Engagement terms/identity/time are protected by SQL update triggers. No hard-delete API exists; history FKs use RESTRICT.

Apply/accept require current ACTIVE verified WORKER, minimum profile, required skill levels and no self-ownership; new Offers require current ACTIVE verified EMPLOYER and live management authority. No matching score, schedule-overlap/location/pay gate is added. Suspended parties may only start/request/confirm/cancel their existing active Engagement obligations, with current role/ownership/state checks. Banned Engagement exceptions remain D5 and fail closed; reducing pending recruiting exposure via withdraw/decline/revoke or scoped Job finalization does not create work.

Structured snapshots carry exact VND strings, dates/timezone/schedule, terms version and historical owner display; accepted terms also carry Worker display. Allowlisted DTOs exclude internal owner ID, user ID, cancellation actor ID, auth/email/phone, raw profile availability and moderation metadata. Cancellation reason is bounded party-visible text and never logged. Detail reads may normalize expiry but never mark VIEWED; marking viewed is an explicit authenticated action. Expiry uses the database clock in UTC; action correctness does not depend on cron or browser time.

The existing 16 KiB JSON limit, strict Zod fields, exact origin, no-store/no-referrer and safe shared errors remain. HTTP tests retain real sessions/status/role checks and intercept only mail transport in the test child. Phase 5 introduced no contact release, admin force action, moderation case system, messaging/outbox, uploads, deployment or production local persistence. Phase 7 communication is described below. See PHASE_5 for verified outcomes.

## Phase 6 search/matching controls

Search is PUBLISHED-only inside parameterized SQL. Strict query keys, Unicode NFC normalization, 200 characters/20 tokens, no tsquery operator syntax, max 30 page and bounded typed filter-bound cursors reject excessive/invalid inputs. Compensation comparisons require explicit pay unit and exact BigInt bounds. The query never interpolates user SQL or logs query text. Rehydration uses the existing public field allowlist and current visibility. No private Worker, auth, contact or message text is indexed.

Private recommendations require fresh ACTIVE role/profile. Worker identity comes from the real session; own/current Company and already-applied Jobs are excluded in SQL. Employer target Job management is derived from current personal ownership or Company membership under the established locks, never creator provenance. Targets must currently opt in, be ACTIVE and have WORKER; an existing Application does not override discovery opt-out. ADMIN alone has no bypass. Current scope is reapplied before cursor processing; cursors never grant access. No Worker-ID score API exists.

Candidate DTOs allow only discovery fields, profile completeness and safe component percentages/reason codes; no identity userId, email, phone, bio, raw weekly windows/timezone, moderation or auth fields. Overlap percentage is deliberately disclosed as a coarse matching explanation, never the underlying schedule. Seven weights are fixed/versioned; unknown pay/experience remain uncovered, with Phase 8 trusted rating/history below. Scores are advisory compatibility, not capacity, verified-email authorization or hiring probability. Apply/accept retain all Phase 5 rechecks.

Minimal new-Application match metadata is calculated server-side inside the existing apply transaction and frozen by SQL; no client score fields are accepted, no historical backfill occurs. It is exposed only through existing self/current-management hiring DTOs. Queries have no shared result/authorization cache and hydrate at most 200 candidates, returning at most 30. Existing origin/no-store/no-referrer/error/logging controls remain. Performance/rate budgets before public launch, D5/D7 and deployment are not claimed resolved.

## Phase 7 chat/contact controls

Every chat read/send/read-marker/block resolves a fresh relevant role, non-BANNED actor and Application entitlement, Worker ownership or personal employer/current Company OWNER/MANAGER. No ADMIN bypass, arbitrary DM, discovery chat, participant-ID payload or stale recruiter grant. Removed role denies that side; departed manager loses list/history/send immediately on subsequent requests. Worker discoverability does not revoke an existing Application. Company creator provenance grants nothing. Message author/side is server-derived; output omits User/auth IDs, email, phone, membership, schedule and moderation data. Context names are voluntary user text, not a PII-redaction guarantee; users may type contact text, without automatic contact release/scanning.

D6 minimal policy: pre-engagement active APPLIED/VIEWED/SHORTLISTED/OFFERED permits chat, including PAUSED/CLOSED pending hiring. REJECTED/WITHDRAWN/CANCELLED or terminal Engagement makes existing history read-only. ACCEPTED Application requires an active Engagement to send. ACCEPTED/IN_PROGRESS Engagement preserves scoped chat despite block, CLOSED, discovery opt-out and actor suspension (even a trusted valid active record under a CANCELLED Job). BANNED actors cannot read/send; banned personal counterpart/Worker denies sends, and detailed banned exceptions remain D5. Relevant current role/ownership remains required; no role-removal bypass. Suspended actors may read existing entitled history, but create/send only in active-obligation context. No dispute/admin force feature is implied.

UserBlock is directional unique User pair, no self-block. Block/unblock targets the actual opposite-side author of a message in an authorized conversation; no arbitrary User directory/ID entrypoint or full block graph. Before active work, either direction disables sends, retains history and does not change Applications/Offers. For Company, any block between Worker and a CURRENT Company OWNER/MANAGER disables pre-work sends for the whole Company conversation, preventing recruiter-switch bypass; departure removes that member from the context's block calculation but preserves their UserBlock. During active work the chat exception is relationship-scoped; terminal work restores read-only/full block. Future invitations must honor this same contact boundary; no invitation exists now.

Message text is 1 meaningful character to4000 UTF-16 characters, CRLF/CR→LF, disallows invisible-only and unsupported C0/control content. React plain escaped text, no raw HTML/Markdown/embed/upload/search. Exact-origin + strict JSON16KiB + strict query/path/body fields protect writes; before/after Message UUIDs are resolved only inside the already-authorized conversation, max50/page. Polling runs only visible client page every8s, abort/no overlap, bounded local state. Forbidden polling clears displayed chat; previous authorized history is not a grant for future requests. No token/message/body/contact/SQL logging introduced.

Send/read/block serialization is database backed; currentActor NO KEY UPDATE preserves role/status exclusion while allowing recipient FK locks safely. Company and Job locks serialize membership/hiring changes; Worker-contact advisory lock serializes block/send across related Jobs. Message idempotency rechecks authorization before replay and rejects changed body. Shared rate limits enforce30 messages/user/conversation/min and60/user/min, not client throttles; replay is free, repeated bodies with different keys consume normal budget. No ML/auto-ban. Notification privacy rechecks owner and current context/role on list/read; no Company fan-out, no full message payload, only safe internal hrefs. Coalescing and monotonic read prevent old-tab notification loss. No email delivery/preferences/outbox infrastructure is claimed. Retention and broader moderation remain deferred.

Server deny-by-default policy checks auth+role+current owner/company membership+resource state+field projection. IDOR protection in private reads/counts/exports and mutations; no frontend-only auth. Company creator departure cannot retain private access. Worker discovery only authenticated Employers with opted-in profiles; never contacts/home address/raw schedule/private metadata. Compensation display follows preference, matching uses only permitted data. No CV/identity/business documents V1.

Suspended users cannot publish/apply/invite/new offers/unrelated conversations. Phase 5 scopes existing active work actions as above; future chat/dispute/block exceptions belong to their owning phases and cease after active work. Admin FORCE actions require case/reason/actor/time/immutable audit. Phase 8 reviews are immutable; future moderation is hide-only. Email verification gates apply/accept/publish/new Offers; phone remains optional alpha with review before public launch D4. Future services must use current auth and resource policies independently.

## Phase 9 moderation controls

Every ADMIN route/service requires real session, fresh ACTIVE status and current ADMIN role, with no normal-role bypass, registration grant, trust in client actor fields or dependency on Company membership. GETs project safe bounded metadata; private investigation is a case-bound POST with reason and immutable CASE_CONTEXT_READ audit. One reported Message body may be returned, never arbitrary conversation history, credentials, sessions, email or broad User search. Case reports/reporter display are ADMIN-only; own receipts exclude identity/admin reason/resolution note. Application-context forms derive the counterparty server-side. Report targets are authorized before deduplication; unrelated private IDs return NOT_FOUND.

All moderation writes use strict Zod schemas, exact origin, explicit action allowlists and 16 KiB JSON boundary. Lists max50/default20 and stable cursors; invalid/duplicate queries fail safely. Text is bounded plain text rendered through React escaping. Private account/reports/admin/API headers use no-store and no-referrer. No attachment/raw HTML/upload channel exists. Reports persist a 10/hour actor budget with duplicate retries free; hitting the limit never punishes an account automatically. Dedicated ADMIN throttling/SLA/appeal automation is deferred, with no invented legal promises.

BANNED fails closed across normal marketplace reads/writes; previously approved own discovery opt-out and scoped Job pause/close/cancel/eligible completion remain exposure-reducing exceptions. History and auth/account access remain. SUSPENDED keeps the established scoped active Engagement start/request/confirm/cancel/chat/dispute exception, denies new recruiting and reviews. No unban endpoint exists. Job hidden state blocks new acceptance even for CLOSED pending Offers; ordinary visible CLOSED acceptance remains approved. Later banning a reviewer does not implicitly hide their historical review. Company has no invented ban state; act on User or open a separately bound Job case.

Resource action + audit commit in one transaction and fail together. Audit reasons are business records; logs include only static action, opaque actor/resource/case/request IDs, outcome/duration, never reasons/messages/details/PII. User status races use NO KEY UPDATE and shared owner/resource locks; observed PostgreSQL lock-wait tests cover publish/apply/send/review vs suspend, hide vs publish/apply, and forced capacity races. Current membership, scope, visibility and state are rechecked server-side. D7 retention and provider least privilege remain separate operational work.

## Phase 8 review controls (historical phase behavior)

Creation requires current ACTIVE relevant role and real completed work; current personal ownership/Company OWNER or MANAGER, not creator provenance. Suspended/banned cannot submit after work ends; blocks do not suppress otherwise eligible review and create no contact channel. User→owner→Job→Application→Engagement locks serialize suspension/revocation and duplicate manager submissions; UNIQUE engagement/direction is final slot protection. Replay is exact normalized payload, key and same actual actor after fresh authorization. No edit/delete/hide/reply endpoints or ADMIN bypass.

Rating integer1–5, optional trimmed max2000 UTF-16 text, well-formed Unicode, control/invisible-only rejection, React escaped plain text. No SQL/body/token/cancellation-actor logging. Existing exact Origin, strict method/body/query/JSON16KiB, safe allowlisted errors and no-store/no-referrer remain. Review DTO reconstructs only safe historical displays/Job title from Engagement snapshot; no raw snapshot, identity/profile/Company internal IDs, creation keys, hidden/status metadata or contacts. Worker reviewers are generic completed-work authors, not public profile links; Company reviewers show Company identity, not private manager. Voluntarily typed personal text is not automatically redacted.

Anonymous PUBLISHED Job gets owner aggregate/count only. Full owner text requires ACTIVE WORKER. Full Worker reviews require ACTIVE EMPLOYER/profile plus current discovery opt-in/target ACTIVE WORKER or managed Application relationship; opt-out denies arbitrary review detail while current hiring retains relevant scope. Hidden reviews are excluded from normal lists, own relationship views, aggregates and matching. Account suspension does not erase historical visible facts; public banned-owner visibility stays D5. Company history survives departure and is never mixed into the creator's personal rating. Review creation does not reopen completed chat or add notifications; moderation/report/admin/hide semantics and retention remain later phases.

## Future threat controls / deferred operations

IDOR/privilege escalation: scoped repository+DTO, role grant isolation, negative authorization tests. XSS: escaped text/sanitizer where required; production CSP design later. CSRF: provider session/origin/sameSite checks and signed webhook validation in auth/integration phase. Abuse/scraping/spam: bounded queries, shared rate controls and case risk flags, thresholds D5/D8; no instance-memory security promises. Avatar/logo when needed: size/type/magic-byte checks and safe images; no general document or malware subsystem. Private media needs scoped signed access, public projection explicit.

No sensitive logs/analytics; PostHog/Sentry integrations Phase 11 with PII scrub. Secret rotation, incident contact, access owner, DB backup/TLS/region and operational response D8 before production. Legal retention/anonymization/export D7, not Foundation blocker; transactional/audit histories not destroyed by naive cascades. Reporting contact must be supplied by operator, not invented. Foundation is not a completed security review for the future marketplace.

Package scripts use verifyDepsBeforeRun=error to fail on stale dependencies rather than auto-install during checks. pnpm-workspace.yaml permits build scripts only for Prisma engines/CLI and esbuild; minimum-release-age exceptions are exact chosen stable Next versions, not wildcard allowances. Lockfile supply-chain policy and peer checks passed. Logger formatter is pure/unit-tested separately from its server-only production entrypoint.

# Architecture

## Phase 11 analytics boundary

The server-only analytics module owns read-only cross-domain aggregate SQL and safe count DTOs, with no imports of another module's repository. It is explicitly observational: domain services remain the authorization/lifecycle source of truth. One RepeatableRead read-only transaction checks current ACTIVE ADMIN and captures DB time for all dashboard facts. UTC [start,end) ranges are limited to 366 days; SQL aggregates do not materialize Applications in Node.

Shared observability contracts are typed and runtime allowlisted. Owning services enqueue only explicit event intents at actual writes. Each transaction attempt has its own WeakMap buffer, discarded on rollback; providers run only after successful commit, outside the retry catch. Noop is the immutable default. AsyncLocalStorage carries dependency-injected providers only within a request/test, not persistent analytics/session/business state. One bounded 100ms cooperative-abort budget covers each event batch; failures are swallowed, so delivery can be lossy. There is no detached background loop, external call in a transaction, event table or mandatory outbox.

Static operation hooks measure coarse duration buckets. API failure boundaries forward only INTERNAL as a new generic exception plus generated request ID; expected errors and original error/stack/cause/body are never forwarded. Readiness observes PostgreSQL only; liveness has no DB/provider dependency. Actual external PostHog/Sentry adapters, privacy/region/retention credentials and alert routing remain Phase 12 operational work. See PHASE_11 for D9 formulas and executed evidence.

Read [PRODUCT](PRODUCT.md) and [PHASE_0](PHASE_0.md) first. APPROVED is product/architecture decision; DESIGN PROPOSAL is implementation guidance; DEFERRED refers to Phase 0 D1–D9. Phases 0–11 are approved. Phase 11 adds Analytics + Monitoring as recorded in PHASE_11. Earlier phase sections are historical, superseded only by explicit later policies below. Phase 12 readiness/public deployment is authorized only for the user-owned project; stop at Phase 12. Actual cloud evidence and blockers are in PHASE_12.

## Approved direction

Next.js App Router + TypeScript strict + PostgreSQL/Prisma, Tailwind/shadcn, modular monolith. Better Auth email/password with verified email gates belongs to Phase 2. Normal dual profiles, operational admin, optional company job ownership, split Application/Offer/Engagement, immutable terms, atomic quota/capacity, per-engagement reviews, job-scoped accepted-invitation chat/polling and privacy policies remain approved, not reopened.

## Foundation implementation

`src/app` contains presentation/HTTP adapters. `src/components/ui` documents shadcn manual setup; tokens/config/utils exist, no unused primitive set. `src/modules/README.md` defines module boundaries. `src/shared/config` contains Zod env parsing and server-only env reader; `shared/db/client.ts` is lazy/server-only with hot-reload reuse and bounded pg pool; `shared/errors` provides client-safe categories; `shared/logging` fixed-field JSON events; `shared/ui` class merging. `scripts/db-smoke.ts` is an operator-only check, not an HTTP endpoint.

Landing/auth UI and build require no DB or provider env. Actual auth validates runtime config lazily; actual Job data requires migrated runtime PostgreSQL. No secrets are read in Client Components. Local system fonts avoid build-time remote downloads. No middleware pretending auth exists.

## Phase 2 implementation

`modules/auth` owns a server-only Better Auth factory/entrypoint, strict HTTP boundary, session-to-current-principal service, controlled normal-role grants and pure policy/config helpers. The app uses same-origin POST fetches against the Better Auth HTTP handler; it does not implement its own credential/session protocol. `shared/email` defines the auth-mail interface and native-fetch Resend adapter. Only tests use fake in-memory delivery. Next `after` retains provider background work on managed hosts; failures produce only a fixed safe event. Phase 2 introduced auth mail only; Phase 7 below adds transactional in-app notifications. Asynchronous outbox remains deferred.

Authentication uses PostgreSQL sessions with cookie cache disabled. Each protected account request validates a real session and reads current roles/status from the DB. Role activation derives user ID from that session and locks/rechecks User in a transaction before idempotent upsert. Policies distinguish authenticated account access, any-of role checks, verified email and ACTIVE new-activity eligibility. Future ownership/company/resource-state checks remain in their owning services, not a speculative permission engine. ADMIN has no public grant path; BANNED full semantics remain D5.

The public auth endpoint surface is explicitly allowlisted. Verification email links open a page with a token fragment; user confirmation POST invokes Better Auth's internal verification handler. No public mutating verification GET, token URL access logs, external redirect input or raw auth result DTO. `/account` is dynamic/server-checked; UI redirects and disabled controls are UX only. Production uses explicit HTTPS APP_URL, injected secret and cloud PostgreSQL; `pnpm start` has no loopback binding assumption. Real DB/auth and actual Next HTTP evidence passed; see the approved [PHASE_2](PHASE_2.md) report.

## Phase 3 implementation

`modules/profiles` owns explicit Zod contracts, server-only services and self/discovery DTOs for WorkerProfile, EmployerProfile, controlled Skill/WorkerSkill, normalized preferences/work modes and hourly weekly availability. Completeness is computed from required fields on each read/save, never persisted or accepted from the client. `profiles/access.ts` exposes a transaction-scoped EmployerProfile prerequisite to Company services; no cross-module repository import exists. `modules/companies` owns Company/CompanyMember, role policy, atomic company/OWNER creation, stable random-suffix slugs, idempotent creation keys, current-membership management and OWNER-only removal of MANAGER. Slug uniqueness conflicts retry the whole transaction at most three times.

Sensitive mutations lock/re-read User first (shared with normal-role grants), then Company where applicable, then re-read current membership/resource. Removing a MANAGER takes that same Company lock. Status/role/membership are never trusted from a cached principal or creator provenance. Company rows survive creator departure. No public member-add, invitation, ownership-transfer, verification or admin-bypass endpoint exists; initial OWNER is atomic and cannot be removed through public APIs. Future membership/moderation writers must preserve this lock protocol.

The dynamic Node `/api/marketplace/[...path]` adapter accepts only explicit method/path/body/query combinations, real authenticated sessions and same-origin mutations. `/worker/profile`, `/employer/profile`, `/employer/workers` and `/employer/companies` call the same services from server rendering; interactive forms receive allowlisted DTOs only. Private pages and APIs use no-store; profile/company pages use no-referrer. Discovery is private, ACTIVE EMPLOYER + EmployerProfile only; target must remain ACTIVE WORKER and explicitly opted in. No contacts, identity IDs, raw schedule/timezone, bio or private status are projected. Queries use indexed filters with ordered cursor pages (default 12, max 30); no matching/ranking or public directory.

Phase 3 resolves only the D1 taxonomy/preferences/availability/completeness and D3 defaults/coarse discovery projection described in PHASE_3. New activity fails closed for SUSPENDED/BANNED; own read access and privacy opt-out remain. There are no active hiring obligations in this phase. Real PostgreSQL tests use independent pool connections and observe actual lock waits before committing revocation/suspension; HTTP tests run real Next/Better Auth/PostgreSQL. Only test email transport is intercepted.

## Phase 4 implementation

`modules/jobs` owns explicit contracts, pure lifecycle/ownership/completeness/quota/material-edit policies, allowlisted projections and server-only transactional services. App adapters and client leaves never import repositories or DB clients. Current EmployerProfile is required; personal ownership uses its ID, company ownership uses current OWNER/MANAGER membership. Creator provenance conveys no company authority. Verified email gates publish/resume and active-term edits; unverified ACTIVE employers can prepare drafts. SUSPENDED/BANNED may read owned records and pause/close/cancel to reduce exposure, but cannot create/edit/duplicate/publish/resume.

Every sensitive write locks/rechecks User, then the Company or personal EmployerProfile owner row, then an existing Job. Company revocation takes the same Company lock. Count PUBLISHED+PAUSED under that owner lock before publication/resumption: three per personal profile, separately three per company, irrespective of creator. The optimistic version rejects stale edits/actions. Creation/duplication keys are actor-bound retry keys; they do not grant authority. Children and scalar terms are saved atomically. Trusted future writers must use these locks too; DB quota is a transactional service invariant, not a CHECK across rows.

Public `GET /api/marketplace/jobs` and `/jobs/:id` project only PUBLISHED ads. Private `/api/marketplace/employer-jobs` separates management DTOs and explicit POST lifecycle actions. All queries are bounded UUID cursor pages; no ranking/search engine. Public owner display includes Company name/slug/badge or personal display name, never owner identity IDs, contacts, membership or status. Job ad text is employer-supplied and escaped, not automatically PII-redacted. No exact address is stored. Public listing is status-based; automatic hiding on owner suspension remains D5, with restrictive owner actions already available.

`JobTerms` v1 is an explicit JSON-serializable contract (money as integer strings, date-only ISO strings, normalized skill/schedule arrays). Phase 4 originally prepared snapshots/material-edit context without persisting hiring records; Phase 5 below activates it from real rows. Description wording alone remains non-material. CLOSED cannot reopen and CANCELLED/COMPLETED remain terminal; Phase 5 adds guarded finalization from CLOSED. No scheduled auto-completion.

See [PHASE_4](PHASE_4.md) for decisions, live evidence and deferred hiring effects.

## Phase 5 implementation

`modules/hiring` owns three separate entities, explicit action policies, strict contracts, safe DTOs, immutable snapshot serialization and server-only orchestration. Jobs exposes its transaction-scoped current-owner guard; profiles exposes its existing safe projections. Jobs imports only `hiring/job-query` for real Application existence, occupied Engagement counts and transactional recruitment cleanup. That public query never imports either service, keeping the dependency acyclic. There are no cross-module repository imports or speculative empty services.

All writes and expiry-normalizing detail reads use User actor → Company/personal EmployerProfile → Job → Application → Offer → Engagement. Worker operations also lock the owning Company/profile before Job, then recheck self-application/current membership. No second User is locked. Membership removal and profile/status writers serialize on their established owner/User rows. Every capacity-changing operation holds Job; counts come from actual ACCEPTED/IN_PROGRESS/COMPLETED Engagement rows. Application/Offer/Engagement unique/composite constraints and immutable SQL triggers protect history.

Offer acceptance rechecks current verified ACTIVE Worker/profile/skills, expiry using database clock explicitly converted to UTC, Job PUBLISHED/PAUSED/CLOSED and available slots. It accepts Offer/Application and creates one immutable Engagement in one transaction. Retry returns the same relationship. Expired acceptance returns its conflict after committing expiry normalization, avoiding rollback of the EXPIRED state. Lists project overdue latest Offers safely; detail/action touches persist expiry under locks. No cron dependency.

Phase 5 resolves only required D2: PAUSED preserves existing hiring; CLOSED forbids new Offers but honors pending ones; decline/revoke/expiry returns OFFERED→SHORTLISTED; rejection requires revoke first; either party can cancel active work with bounded stored reason. Employer starts, Worker requests, Employer confirms. Job cancellation blocks active work; CLOSED→COMPLETED requires at least one completed Engagement and no active ones. Both finalizations clean outstanding recruitment in the same transaction. The first Application activates real material-edit restrictions, including conservative headcount freeze; description wording remains editable.

Dynamic Node pages and the existing exact-origin, authenticated API expose explicit actions only. Snapshot DTOs remove internal owner IDs and actor provenance. Worker hiring projection reuses safe discovery fields plus completeness, independent of public discovery opt-in because the Worker applied to this Job. Contact/auth data, private schedule and moderation metadata remain excluded. Production needs only injected env, managed PostgreSQL and existing email provider; no production filesystem, local process, cron, deployment or Phase 6 capability.

## Phase 6 search and matching

Jobs exposes a public PostgreSQL FTS query through its existing service, sharing the explicit public Job projection. SQL owns a generated, NFC/Unicode-lowercased weighted title/description vector and PUBLISHED-only GIN index. Query text goes through strict validation and bound plainto_tsquery; relational filters compose before ranking. An integer micro-rank, publication timestamp and ID form filter-bound keyset cursors. The derived column is deliberately absent from ORM inputs; migration SQL is authoritative for it. PostgreSQL 18 UTF8 is the verified minimum because pg_unicode_fast makes Unicode case mapping independent of database locale. No external search dependency exists.

Matching separates a pure versioned scorer/config from private server-only recommendation services. The scorer receives validated Worker/Job DTOs plus an explicit evaluation instant; it never reads DB or auth. Hiring imports only that pure scorer for minimal immutable match-at-apply metadata inside its existing eligibility/capacity transaction. Recommendations use public Jobs/profiles projections and the existing current-owner service, with no cross-module repository imports or Jobs→matching-service cycle. Required skills are SQL-prefiltered, then completeness/skill eligibility rechecked by the pure scorer. Account/ownership/opt-in scope is service-owned, independent of score.

Phase 6 initially measured only skills, recurring overlap and coarse location; its four future components were uncovered. Phase 8 below activates trusted reputation inputs without changing historical snapshots. Exact positive rational arithmetic determines final rounded score; explanations/coverage/version/time accompany it. Same-zone recurring hours compare locally. Different zones use Job-start reference week, otherwise the evaluation week; an hourly offset scan detects DST and leaves differing-zone transition weeks uncovered. A request-local bounded offset cache contains only timezone/week offsets and never authorization/profile data.

Recommendations hydrate at most 200 ID-ordered SQL-prefiltered candidates in batch, rank eligible rows by final score/coverage/ID and page at most 30. Ranking is within that bounded pool, not global; fresh changes may reorder pages. Private reads recheck current status/roles/opt-in; Employer candidate reads lock User→owner→Job and recheck Company membership. Phase 6 introduced no public scoring API, private schedule DTO, materialized pair table, matching cache or metric dashboard. Phase 7 communication is described below. PHASE_6 records the resolved D1 subset and exact formulas.

## Phase 7 communication implementation

`modules/messaging` owns strict message/query contracts, pure policies/projections, PostgreSQL services, read/unread, UserBlock, in-app Notification and polling UI. Hiring exposes `chat-query` as a public transaction boundary for current Application/Job/Worker/Company context; no repository import or service cycle. Conversations are Application-only and lazily created by explicit POST. An Application's unique Worker×Job relationship is the sole entitlement source. Invitation acceptance remains D6, with no invitation/DM endpoint; pending invitation cannot grant access. Existing Application context does not require discovery opt-in.

Writes and scoped history reads lock actor User with NO KEY UPDATE, then a namespaced PG transaction advisory lock for the relationship's Worker contact scope, then Company/personal EmployerProfile→Job→Application→Conversation. No second User/Profile row is exclusively locked. The contact lock serializes block/send across this Worker's Jobs; it has no process-memory state. Every hiring-state writer already holds Job and every membership removal holds Company. User NO KEY UPDATE still conflicts with role/status writers and permits recipient FK KEY SHARE during two-way sends; the shared currentActor guard uses that mode too. Trusted writers must not lock a User FOR UPDATE and then wait for owner/Job locks; use NO KEY UPDATE for unchanged identity keys. User-only moderation/grant locks remain compatible with this protocol.

Send atomically authorizes fresh identity/role/current membership, active work/status/block policy, idempotency and DB-backed rate budget, then writes immutable Message, lastMessageAt and optional recipient Notification. A conversation's message times are strictly increasing millisecond UTC database-clock positions under its lock, with ID tie-breaker for legacy/direct records. No external asynchronous side effect exists, so durable in-app notifications are written directly in that same transaction: no outbox/daemon/cron/email/preferences claim. Coalesce one unread NEW_MESSAGE per conversation/recipient; store IDs, not message body or JSON payload. Company manager messages notify Worker; Worker→Company relies on each current manager's inbox unread state instead of fan-out. Personal employer receives a direct notification.

Company ownership/current OWNER/MANAGER scope survives recruiter changes. Actual sender User and side are stored internally; DTO exposes display, side, own flag, plain text and time only. Per-user durable read position advances only to a message in this conversation and never backwards. Mark-read and coalesced notifications serialize with sends; an old tab does not clear notification for a newer message. Unread excludes only the current User's messages, including messages by other Company managers as unread until that User reads them. Inbox totals use current-scope SQL on explicit inbox access; static navigation does not scan counts.

Polling is client-only every 8 seconds on a visible chat page, aborts on cleanup, never overlaps, and uses authorized server Message IDs as before/after cursors with timestamp/ID ordering. Recent/older/forward pages default 30/max50; client holds max200 recent messages and one bounded older page, pausing polling while browsing history. Dedupe by ID; send retries retain creationKey/body. No WebSocket/SSE/presence/upload/background polling. All runtime state is in PostgreSQL, compatible with managed Node/Next independent of developer PC. D6 terminal/block/status policy and exact bounds are in PHASE_7/SECURITY; future notifications/email/accepted invitations remain explicitly deferred.

## Phase 8 reviews and reputation

`modules/reviews` owns strict input, immutable review creation, safe list DTOs and versioned `reputation-v1` facts. Hiring exposes `review-query` as a public scoped transaction boundary, preserving User NO KEY UPDATE → owner → Job → Application → Engagement locks. Current ACTIVE Worker/personal employer/Company OWNER or MANAGER may consume one direction slot after COMPLETED; blocks are unrelated to this post-work action. DB uniqueness and insert/update guards validate relationship/target/scale and freeze history. Reviewer User is accountability only; Company is the stable author/target and Engagement snapshot supplies historical safe display. No admin/hide/delete/reply/notification side effect exists.

`reviews/query` is a server-only public facts boundary with no service/UI imports. One bound SQL statement batches up to 200 Worker rating/history aggregates in a consistent statement snapshot. Matching services and hiring apply explicitly pass integer sum/count/completed/worker-cancelled facts into the pure scorer; no DB reads in the algorithm, cross-module repositories, cache or per-candidate queries. Rating = (sum-count)/(4count); reliability = completed/(completed+Worker-caused cancellations). Zero denominator is uncovered; compensation/experience remain uncovered. Exact rational math remains, weightsVersion v1, algorithmVersion deterministic-v2, max coverage 80. Old v1/null snapshots are never rescored/backfilled. Owner aggregates are separate Company/personal query projections with completed-hire count; employer cancellation attribution/completion-rate sophistication is deferred.

Public PUBLISHED Job detail exposes owner rating/count/completed count only. Full owner review text requires ACTIVE authenticated WORKER; Worker reviews require ACTIVE EMPLOYER/profile and current opt-in discovery or current managed Application context. No anonymous Worker directory or public Worker review author navigation. Lists are target-bound timestamp/UUID keysets (20 default, max30); hidden records are excluded. Server rendering and client composer are separate; client receives only side/Engagement ID. All runtime state remains managed PostgreSQL/env/Node; no PC worker or deployment.

## Phase 9 reports, moderation and admin

`modules/moderation` owns report intake, case workflow, safe ADMIN/own-report DTOs and immutable audit orchestration. Explicit domain boundaries in auth/jobs/hiring/reviews/messaging own resource policies and mutations; no cross-module repository import or generic status patch API exists. App routes are authenticated transport; client forms import contracts only. Case context is an audited, reason-required POST returning one bound resource, never arbitrary User search or conversation history.

Mutation order is User NO KEY UPDATE → current Company/personal EmployerProfile → Job → Application → Offer → Engagement → Review → Case → Report/Audit. Each action uses only its needed prefix. Account moderation first locks the sorted distinct actor/target User IDs, then the target's personal profile and current Company rows in sorted order. These owner locks serialize ban visibility with Apply/accept. Case read before resource locks is preliminary; exact target/state is rechecked under the Case lock afterward. Company membership removal retains the same Company lock; ADMIN needs no membership.

Fresh ACTIVE ADMIN is checked in every service transaction and audit INSERT guard. Reporting needs a fresh normal role and an accessible target, with actual owner/resource locks for Job/Review/Company/Engagement/Message. Application-context reporting derives the opposite User or Company entirely server-side and rechecks relationship on intake; raw account IDs do not enter those forms. One unresolved report per reporter/target is enforced by a partial unique index; retries reuse it without consuming the 10/hour DB-backed budget. Case linking never mixes targets. Case close resolves/dismisses linked reports atomically.

Moderation visibility overlays Job lifecycle. Hidden Jobs block new apply/offer/accept/publish/resume, public detail/FTS/recommendations and candidate recruiting; existing work/history remains. Personal banned employers are excluded; Company visibility depends on at least one current non-banned OWNER/MANAGER with EMPLOYER role, never creator provenance. Suspension alone does not hide an ad. BANNED denies normal marketplace services; approved own discovery opt-out/scoped Job exposure reduction and account/auth remain available. Suspended actors preserve existing scoped obligation paths, never new review/recruiting.

Review INSERT authority remains Phase 8's guard; a new UPDATE guard permits only audited hiddenAt flips while freezing all content/targets. Reputation reads committed visible rows on demand; no cache/backfill/rescore of historical Application snapshots. FORCE_COMPLETE requires IN_PROGRESS and creates no fake Worker request; FORCE_CANCEL permits ACCEPTED/IN_PROGRESS and no participant cancellation attribution. Job capacity and immutable terms use existing locks/constraints. Both terminal outcomes stop new chat. See PHASE_9 for D5 decisions and verification.

## Future boundaries — design proposal

Worker/employer/admin route groups introduced only in owning phases. Server Actions/Route Handlers validate/authenticate and call services. Services recheck ownership/current company membership/state in scoped queries/transactions; repositories never authorize browser-supplied IDs alone. Return DTO allowlists, not raw Prisma entities. Client components are only interactive leaves. Cross-module calls use public contracts/services; applications owns hiring orchestration.

Phase 3 verifies User→Company lock ordering and membership revocation on PostgreSQL. Phase 5 extends the same order through Job/Application/Offer/Engagement for hiring. No generic domain locking framework exists. Phase 7 writes durable in-app notifications with Message in one transaction; an outbox remains deferred until external asynchronous delivery is needed. Future email/storage/search/transport adapters remain replaceable without moving product rules into providers. Company conversation/review subjects use stable owner entities, not creator user IDs.

Suspension/block is action+resource policy: deny new activity while preserving required active-obligation access; no blanket UI/session gate. Admin FORCE actions require case/reason/actor/time/immutable audit. Full authorization and audit services are not implemented in Foundation.

## Phase 10 hardening

The owning modules and public DTO boundaries stay intact. Shared pure helpers own plain-text validation, rate configuration, database-code classification and header construction. Server-only helpers own atomic RateLimit SQL and bounded database-only transaction execution; they do not become a new business module. Domain services continue to authorize current actor, role, membership, state and visibility under canonical locks. ADMIN is not an implicit normal-role or discovery bypass.

Domain transactions use a 5s acquisition wait, 10s execution budget (15s for existing matching/moderation work), at most three attempts, and small bounded jitter. Only confirmed PostgreSQL serialization/deadlock aborts (40001/40P01, Prisma P2034) retry the entire callback in a fresh transaction. Connection loss, ambiguous commit, timeout, arbitrary exceptions and auth/email provider calls never automatically retry. Audit, notification and primary state still commit together.

Persisted counters use one parameterized PostgreSQL INSERT/conditional ON CONFLICT statement and database time, including first-key contention. Better Auth retains its provider rules through custom storage, avoiding provider-wide expiry pruning of business namespaces. Marketplace counters use fixed windows; auth preserves provider sliding last-request semantics. GET hiring detail/history now projects overdue pending offers as expired without writing; mutations still normalize under locks. Provider session housekeeping remains provider-owned.

Version 1 Offer/Engagement text decoding retains the historical contract; stricter text normalization applies to new ingress. No immutable historical snapshot, migration, PRODUCT decision or lockfile was rewritten. Global CSP allows Next inline bootstrap explicitly, omits eval in production, and leaves nonce-based strict CSP for a separately designed rendering change. See SECURITY and PHASE_10 for limitations.
